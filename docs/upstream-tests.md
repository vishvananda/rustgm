# Upstream Rust test research and import policy

Investigated 2026-10-11. Imports are pinned, never fetched from a moving branch
during tests. See `third_party/sources.json` for exact revisions and checksums.

## Primary source: rustc

[rust-lang/rust tests/ui](https://github.com/rust-lang/rust/tree/1.98.0/tests/ui)
is the strongest broad source: lexer/parser, macros, traits, generic associated
types, const evaluation, borrow checking, closures and async regressions. The
[compiler testing guide](https://rustc-dev-guide.rust-lang.org/tests/intro.html)
explains its compiletest-based organization.

Pinned release: **1.98.0**, commit
`88d9e12ae178fab0fb5cc050a94da85685d449ea`. The first import takes five lexer
tests, unchanged: scientific notation, NFC spellings, Unicode whitespace and
two unterminated-comment regressions. Three are whole check-pass programs;
two are compile-fail programs. `make test-rustc` checks these independent
outcomes with the pinned compiler, while our PA1 tests grade lexical output.

Upstream directives are not decoration: editions, revisions, auxiliary crates,
target restrictions, feature gates and flags affect applicability. Classify
them before importing. Do not run arbitrary upstream directives through a
shell. Curate stable cases into explicit manifests and retain needed companions.
Borrow tests need both accepted and rejected programs: rejecting everything
cannot establish correct borrowing. Avoid nightly/rustc-internal tests unless
the course assignment explicitly adopts their feature.

Do not adopt rustc's `.stderr` as our diagnostic contract. It includes compiler
wording, suggestions and display details unrelated to language conformance.
Use independently declared acceptance/rejection and our own deterministic
text diagnostics. Runtime checks compare only defined, promised behavior.

## Early source: rust-analyzer

[rust-analyzer parser test data](https://github.com/rust-lang/rust-analyzer/tree/2ad81e72b7e978cb800dffe1bcce5c9f98032acf/crates/parser/test_data)
contains compact lexer and parser fixtures, including incomplete/error inputs.
The current directories are `crates/parser/test_data/lexer`, `parser` and
`generated`; older documentation sometimes names `crates/syntax/test_data`.

Pinned commit: `2ad81e72b7e978cb800dffe1bcce5c9f98032acf`. Thirteen unchanged
lexer fixtures seed PA1. They are lexical fragments, not necessarily programs
rustc accepts. An upstream lexer `ok` file may contain numerically invalid
literals because interpreting values is a later responsibility. Keep that
distinction explicit in our manifest and handout.

Rust-analyzer's `.rast`/`.txt` trees are not our AST format, and recovery-oriented
parser acceptance is not proof of successful language compilation. Reuse the
source challenges and independently specify our token/AST text oracle.

## Coverage source: Rust Reference

The [versioned Rust Reference](https://doc.rust-lang.org/1.98.0/reference/)
supplies the language-rule coverage matrix and examples. It is not a complete
executable conformance suite. Write minimal original tests for each owned rule,
pair rejection with acceptance, and add interactions at the earliest assignment
that owns all their features. Record rule IDs alongside fixtures as the handouts
are made normative. Rustc and documentation disagreements need investigation,
not automatic reference regeneration.

## Attribution and maintenance

Both imported projects are distributed under MIT OR Apache-2.0, subject to
individual-file notices. Retain original files and the upstream license texts
under `third_party/`; the Rust COPYRIGHT document describes its exceptions.
The initial selected files have no separate license override. Preserve notices
and recheck licensing per file when expanding imports.

For each import record repository, immutable commit, path, SHA-256, destination,
owning assignment, adaptation and applicability. `make test-upstream` works
offline. `python3 scripts/upstream.py --fetch` explicitly restores only the
listed original inputs after verifying their pinned hashes. Course output
sidecars are generated by our maintainer implementation and reviewed separately.
