## 2. Part 1: a partial impl epoch in the lookahead

### Rule and mechanism

A census lookahead runs the later crate passes after the terminal failure,
with the census parked. When that failure stopped
`validate_trait_implementations`, only the impls validated before it are
`Validated`. Before this batch, a later pass's `Availability::Validated`
selection silently skipped the rest and could read the partial set as
complete. That is census 20's record 6: `Shl<u8> for u8` was the only
validated `Shl` impl, so `1 << 0` selected it and reported "incompatible
types".

- **Flag.** `Generics::partial_epoch` (`sema/generics.rs`) is false except
  inside a lookahead. `Checker::look_ahead`
  (`sema/declarations/passes.rs`) sets it before each pass positioned after
  `validate_trait_implementations` in `PASSES` (now named by the
  `VALIDATION` constant), when the registry exists and
  `!headers_validated()`. It clears the flag when the lookahead ends. A
  lookahead that starts before validation runs validation unflagged, as
  before.
- **Guard.** In `Search::implementation_candidates`
  (`sema/traits/selection/search.rs`), when the flag is set, the query is
  `Validated` and `candidates_for` returned `Ready`, the same goal is asked
  again with `Executable`. Any non-`Ready` answer returns
  `census::PARTIAL_EPOCH`, "trait selection requires the completed immutable
  impl epoch". The text follows record 5's "source receiver compatibility
  requires the completed immutable impl epoch". The registry API is
  unchanged.
- **Record.** `census::look_ahead` records an error whose message is exactly
  `PARTIAL_EPOCH` as `Category::Blocked`, with `blocked_by` the terminal
  record, and adds 1 to the phase's `blocked` count. Every other lookahead
  record keeps its form and changes no count. The `look_ahead` contract in
  `census.rs` and the `passes.rs` module doc state this single exception
  (D2).

**Lane B's read-review** (D3) of the guard answered three questions:

- The `Executable` re-query has no side effect that changes the selection.
  It repeats the `Validated` call's work on the same goal (root path
  compression, an already done materialization, hash-consed interning that
  returns existing ids, read-only bucket scans) and creates no variables or
  unifications. Its only effect is a second work charge, under
  `partial_epoch` only. The guard's comment says so.
- A `Ready` answer under `Executable` has exactly the `Validated` owner set:
  `append_candidates` pushes validated entries in both modes and diverts
  unvalidated ones under `Executable`, which then answers `Unvalidated`.
- The union's negative queries use `Availability::Declarations`, so the
  guard is inert there, and the merge was textual. The union's only
  `search.rs` hunk is the line-40 re-export, and the rebase applied with no
  conflict.

**Why ordinary mode cannot change.** The flag is set only inside
`look_ahead`, which runs only when a census is active and a crate pass has
failed. Ordinary checking, and census mode before its terminal failure, run
the previous code.

## 3. Part 2: elaborated premises

### Rule

Batch 17 certifies only an owner's declared bounds whose normalization
completed. `elaborate_trait_bounds` appends supertrait consequences after
`declared_predicate_counts` at publication, so an elaborated premise was
never certified. Census 20's record 1 needs one: the supertrait condition
selects the `Iterator` impl at `:543`, which needs
`<P as Pattern>::Searcher<'r>: ReverseSearcher<'r>`, and only the elaborated
`Searcher<'a>: ReverseSearcher<'a>` proves it.

The subject-shared rule (D4): an elaborated trait premise in
`predicates[owner][declared_count..]` is certified when

1. a certified declared bound has the same binder count (`Option<u32>`:
   both `Clause::Predicate`, or both `ForAll` with equal bound-region
   counts) and the same interned subject `TypeId`; and
2. its trait application has no projection.

Soundness. The declared bound was certified only after bound normalization
ran under the raw environment, which already held every elaborated premise
and equation. An elaborated premise with that subject whose trait arguments
carry no projection has no projection term besides the subject, so it is
normal for the same reason. Projection-bearing supertrait arguments, binder
changes and other subjects each need their own normalization proof, and
stay uncertified. Each is stricter than rustc and is an open item with a
control: `elaborated-projection-argument`, and the rule's unit test for the
other two. The provenance-and-subset rule was not chosen.

### Mechanism

- `sema/generics/elaborated_certificates.rs` holds the rule. `inherited`
  collects the certified bounds' subject keys in a small `HashSet` and keeps
  the elaborated premises that qualify, in elaboration order.
- `Generics::certify_environment` (`sema/generics.rs`) takes the payment
  now. It returns at once when `normal` is empty, so an owner without
  certified bounds pays nothing. When the owner has elaborated premises, it
  pays the scan (one step per declared and elaborated premise) before the
  scan runs. Then it pays the certificate map's growth for the declared and
  inherited premises, before any certificate is recorded, and certifies
  both through the unchanged `certify_normal_premises`. Exhaustion therefore
  certifies nothing. `certify_source_environment` (`required_features.rs`)
  passes its payment through.
- `types/traits.rs` gains `trait_application_has_projections`, the sibling
  of `trait_application_has_free_regions`. It reads the interned
  application's cached `Projections` property in O(1). The property and
  `trait_properties` are private to `types` (amendment 2).
- There is no new carry site. Certificates stay keyed by clause value, and
  batch 17's carries (`Assumptions::copied`, `opened_certificates`,
  `substitute_observed`) apply unchanged to an inherited certificate.

### Record 1: normalizing `Self::Item` through a rigid-projection requirement

The method's signature names `Option<$iterty>`, while the trait's names
`Option<Self::Item>`. `Self::Item` is
`<RSplit<'a, P> as Iterator>::Item`, and normalizing it in the
`DoubleEndedIterator` impl's environment selects the `Iterator` impl
(`:543`), which requires `P::Searcher<'a>: ReverseSearcher<'a>`. The text
comes from the projection path's selected source
(`sema/projections/cursor.rs:229` or `selected.rs:70`): no unambiguous
validated impl source was found.

The probes (`repro/r1n/`, declarations `declared.txt` sha `638e51b6`, written
before each round ran) mirror the pair without core: `Iter { type Item; fn next }`
and `DoubleIter: Iter { fn next_back(&mut self) -> Opt<Self::Item> }`.
rustc 1.98.0 accepts all seven.

| Probe | Shape | Candidate and census 21 pins | Census 20 pin `6a699887` |
|---|---|---|---|
| `n-sig` | as core, body `Opt::None` | record 1's text at `next_back` | header, requirements text |
| `n-header-only` | body `loop {}` | the same as `n-sig` | header |
| `n-sig-item` | `next_back` written `-> Opt<Self::Item>` | record 1's text | "associated type requires an unambiguous implementation" at the written `Self::Item` (declared header: a mismatch) |
| `n-explicit` | plus a written `P::Searcher<'a>: ReverseSearcher<'a>` | record 1's text (declared accept: a mismatch) | record 1's text, byte for byte |
| `n-where-form` | both bounds as where clauses | record 1's text | header |
| `n-no-bound` | the `Iter` impl without the requirement | accepts | accepts |
| `n-no-item` | no `Item`; the methods return `Opt<u8>` | accepts | header (declared accept: a mismatch) |

The record needs both the `Iter` impl's requirement on the rigid GAT
projection and a `Self::Item` to normalize: dropping either passes. A
written premise does not help (`n-explicit`), and on census 20's pin the
same written-premise probe fails at the same method. The failure therefore
predates part 2, which only let the header pass, and it is not specific to
elaborated premises. The three mismatches are recorded as observed; none
changes this conclusion. The probes reproduce byte for byte on the census 21
pin. This record is batch 19's lead and is not fixed here.
